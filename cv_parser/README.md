# CV Parser v2 - Part 1 of the rebuilt pipeline

## What changed from v1 and why

v1 (`scriptfusion_prototype/skill_extraction.py`) used spaCy's
PhraseMatcher, which had a real, confirmed bug: spaCy's tokenizer splits
symbol-heavy skill names inconsistently depending on surrounding text -
`"c#"` tokenizes as `['c', '#']` right after another word, but stays a
single token in isolation. That silently broke matching for C#, C++,
.NET, Node.js, CI/CD - exactly the kind of skill a technical CV lists.

v2 drops PhraseMatcher entirely for plain regex substring matching with
manual punctuation-safe word boundaries. This is immune to tokenization
quirks by construction - regex just scans the raw string.

v2 also adds a second, complementary pass: it looks for an explicit
"Skills" / "Technical Skills" / "Programming Languages" section header,
extracts the list under it, and reports EVERY item found there - even
ones not in our dictionary (tagged `"uncategorized"`). That's the "pick
up any keyword about skill/programming language" behaviour you asked
for: known skills get categorized, unknown ones get surfaced instead of
silently dropped, so the dictionary can grow from real resumes over time.

## Verified against

- **3 synthetic test resumes** (`test_resumes/`, generated by
  `make_test_pdfs.py`) specifically designed to stress the old bug:
  a technical resume listing C++/C#/.NET/CI\.CD/Node.js in a skills
  section, a free-text resume mentioning symbol-heavy skills in prose
  (no skills section at all), and a resume listing tools our dictionary
  doesn't know (Zephyr RTOS, Unity3D, Godot Engine) to confirm the
  fallback path works.
- **1 real resume** (Janidu De Alwis, from the team's actual form
  responses) - re-confirms the design/web skills it already caught in
  v1, plus catches Excel where before it wouldn't have.

All 4 pass: every symbol-heavy skill is now detected, unknown skills are
surfaced rather than dropped, and no false positives appeared in testing.

## Known limitation (documented, not hidden)

Section-boundary detection depends on line order from `pdfplumber`'s
`extract_text()`. On multi-column resume layouts (like Janidu's, which
uses a two-column design), pdfplumber doesn't always reconstruct reading
order correctly, so a few stray words from a neighbouring column can leak
into the "skills section" extraction. It's capped at 8 lines so it can't
run away, and it only affects the section-based fallback capture - the
main whole-document dictionary scan (which is how most real skills get
caught) is completely unaffected by this. Fixing it properly would need
position-aware extraction (word bounding boxes clustered by column)
instead of flat text - worth doing later if multi-column resumes turn
out to be common in your dataset.

## Files

- `skills_dictionary.py` - 100+ entry skill dictionary (languages,
  frameworks, databases, cloud/DevOps, mobile, testing, design, data/ML,
  web, methodology, version control), plus the section-header lists.
- `cv_parser.py` - the parser itself. Run standalone:
  `python3 cv_parser.py path/to/resume.pdf`
- `../test_resumes/` - synthetic test PDFs + generator script.

## Update: tested against all 7 real collected CVs

Once the team dropped all 7 real resumes into `Final_project/resumes/`,
running the parser against the full batch surfaced one more real gap and
two genuine data-quality issues (not parser bugs):

**Real gap found and fixed: image-based PDFs.** Dumindu Malinga's CV had
zero extractable text (0 characters, one embedded image - it was exported
as a flattened image, not real text). It would have been silently skipped
entirely. Added an OCR fallback (`pytesseract`, already available in this
environment) that kicks in per-page whenever pdfplumber finds no text -
confirmed it now correctly recovers Flutter, Dart, Java, MySQL, SQLite,
HTML/CSS, Git/GitHub from that resume.

**Data quality flag: mismatched resume upload.** "5652 - Chanu Lakshan.pdf"
is genuinely an accountant's CV ("Chanuka Rathnayake, Main Accountant at
MAS Holdings") with zero technical skills - but the email on it
(chanukalakshan111@gmail.com) matches the "Chanuka Lakshan" form
submission. This candidate appears to have uploaded the wrong file. Worth
following up with them directly rather than something the parser can fix.

**Data quality flag: skills section is soft-skills only.** Lashan
Chanaka's CV lists a "SKILLS" section containing only "Critical Thinking,
Group Working, Communication, Time Management" - no technical skills at
all. The parser correctly found nothing except Git/GitHub (picked up from
his GitHub project URLs in the text, not a skills list). This candidate's
resume genuinely doesn't list technical skills - worth flagging so they
can update it before this dataset is used for real scoring.

**Final tally, 7/7 real CVs:** 5 with solid technical skill lists (Chanuka
Lakshan, Dumindu Malinga, Lapalu Liyanage, Sandun Madhushan, Janidu De
Alwis - design-only), 1 with no technical content (Lashan, genuinely
sparse resume), 1 mismatched upload (Chanuka's accounting CV - likely
wrong file, follow up with the candidate).
